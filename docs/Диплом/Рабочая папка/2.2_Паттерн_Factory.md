# 2. Паттерн Factory (Фабрика)

Паттерн Factory (Фабрика) представляет собой порождающий паттерн проектирования, предназначенный для инкапсуляции процесса создания объектов. Данный паттерн решает проблему создания экземпляров классов без указания их конкретных типов, делегируя ответственность за выбор подходящего класса специальному объекту-фабрике. Паттерн Factory является одним из фундаментальных паттернов проектирования, широко применяемых в объектно-ориентированном программировании для обеспечения гибкости и расширяемости системы.

Основная концепция паттерна Factory заключается в централизации логики создания объектов в отдельном компоненте, который на основе входных параметров определяет, какой именно класс должен быть инстанцирован. Это позволяет клиентскому коду не зависеть от конкретных классов создаваемых объектов, а работать с абстракциями, что обеспечивает слабую связанность компонентов системы.

Исторически паттерн Factory был описан в классической работе "Design Patterns: Elements of Reusable Object-Oriented Software" (Gang of Four, 1994) и с тех пор получил широкое распространение в различных технологических стеках и доменах разработки программного обеспечения. В контексте разработанного приложения паттерн Factory применяется для создания редакторов файлов различных типов, обеспечивая единообразный интерфейс создания объектов и упрощая добавление поддержки новых форматов файлов.

## Структурные компоненты паттерна

### Product (Продукт) — абстрактный базовый класс

Продукт представляет собой абстрактный интерфейс или базовый класс, определяющий общий контракт для всех создаваемых объектов. Ключевые характеристики продукта включают определение набора методов, которые должны быть реализованы во всех конкретных продуктах, обеспечение полиморфизма через единый интерфейс, а также инкапсуляцию общих свойств и поведения, характерных для всех продуктов семейства.

Практической реализацией продукта в приложении является класс `BaseFileEditor` (расположенный в `src/editor/base_editor.py`). Данный класс представляет собой абстрактный базовый класс, наследующийся от `QWidget` и `ABC`, который определяет общий интерфейс для всех редакторов файлов. Класс инкапсулирует общую функциональность, такую как управление путем к файлу (`file_path`), отслеживание состояния модификации (`is_modified`), управление стеками отмены и повтора действий (`_undo_stack`, `_redo_stack`), а также определяет абстрактные методы, которые должны быть реализованы в конкретных редакторах: `load()`, `save()`, `save_as()`, `get_content()`, `set_content()`, `undo()`, `redo()`.

Класс `BaseFileEditor` также определяет систему сигналов Qt для уведомления о событиях: `undo_available`, `redo_available`, `modification_changed`, `file_saved_as`, `error_occurred`. Это обеспечивает единообразный механизм коммуникации между редакторами и остальными компонентами системы, независимо от конкретной реализации редактора.

### ConcreteProduct (Конкретный продукт) — конкретные реализации

Конкретные продукты представляют собой реализации абстрактного интерфейса продукта, каждая из которых предназначена для работы с определенным типом данных или выполнения специфических задач. Каждый конкретный продукт наследуется от базового класса продукта и реализует все абстрактные методы, добавляя при этом специфичную для данного типа функциональность.

Практическими реализациями конкретных продуктов в приложении являются следующие классы:

- **STEditor** (`src/editor/st_editor.py`) — редактор для файлов Structured Text (`.st`), который обеспечивает специализированную функциональность для работы со структурированным текстом, включая иерархическое представление данных, синтаксическую подсветку через `STHighlighter`, интеграцию с системой отслеживания изменений файлов через `FileWatcher`, а также поддержку операций с дельта-изменениями через `DeltaProcessor`.

- **MarkdownEditor** (`src/editor/markdown_editor.py`) — редактор для Markdown-файлов (`.md`), который предоставляет функциональность для редактирования и предпросмотра Markdown-документов. Редактор использует компонент `MarkdownViewer` для отображения отформатированного содержимого и `MarkdownConverter` для преобразования Markdown-разметки в HTML, обеспечивая режим разделенного экрана с одновременным отображением исходного текста и его визуализации.

- **PlainTextEditor** (`src/editor/plain_text_editor.py`) — универсальный текстовый редактор, используемый в качестве редактора по умолчанию для файлов с неподдерживаемыми расширениями или для простых текстовых файлов (`.txt`). Данный редактор предоставляет базовую функциональность редактирования текста без дополнительных специализированных возможностей.

### Factory (Фабрика) — класс-фабрика

Фабрика представляет собой класс, ответственный за создание экземпляров конкретных продуктов на основе входных параметров. Ключевые обязанности фабрики включают определение логики выбора подходящего класса продукта, инкапсуляцию процесса создания объектов, обеспечение единообразного интерфейса для создания различных типов продуктов, а также управление реестром доступных продуктов и их сопоставлением с входными параметрами.

Практической реализацией фабрики в приложении является класс `EditorFactory` (расположенный в `src/editor/editor_factory.py`). Данный класс реализует вариацию паттерна Factory Method с использованием реестра (Registry Pattern), что позволяет динамически сопоставлять расширения файлов с классами редакторов. Класс содержит статический словарь `_registry`, который хранит соответствие между расширениями файлов (ключи) и классами редакторов (значения):

```python
_registry: Dict[str, Type[BaseFileEditor]] = {
    '.md': MarkdownEditor,          # Редактор для Markdown-файлов
    '.st': STEditor,                # Редактор для Structured Text файлов
    '.txt': PlainTextEditor,        # Редактор для простого текста
}
```

Основной метод фабрики `create_editor(extension: str, parent: Optional[QWidget] = None) -> BaseFileEditor` выполняет следующие операции:

1. Нормализация входных данных — приведение расширения файла к нижнему регистру для обеспечения регистронезависимого сравнения
2. Поиск в реестре — определение соответствующего класса редактора на основе расширения файла
3. Создание экземпляра — инстанцирование найденного класса с передачей необходимых параметров
4. Обработка неизвестных расширений — возврат редактора по умолчанию (`PlainTextEditor`) для неподдерживаемых расширений

Класс также предоставляет дополнительные вспомогательные методы: `get_supported_extensions()` для получения списка поддерживаемых расширений, `register_editor()` для динамической регистрации новых редакторов, `unregister_editor()` для удаления регистрации, `get_editor_description()` для получения описания редактора, а также `create_editor_for_type()` для создания редактора на основе типа контента (template, folder, file, markdown).

## Механизм взаимодействия компонентов

Взаимодействие компонентов системы при использовании паттерна Factory организовано таким образом, чтобы клиентский код не зависел от конкретных классов редакторов, а работал исключительно с абстрактным интерфейсом `BaseFileEditor`. Механизм взаимодействия демонстрирует практическую реализацию принципов инкапсуляции и полиморфизма в контексте создания объектов.

В реализации паттерна Factory выделяются следующие ключевые компоненты:

- **EditorFactory** (Factory) — централизованная фабрика для создания редакторов на основе расширения файла или типа контента
- **BaseFileEditor** (Product) — абстрактный интерфейс, определяющий общий контракт для всех редакторов
- **STEditor, MarkdownEditor, PlainTextEditor** (ConcreteProduct) — конкретные реализации редакторов для различных типов файлов
- **EditorManager, FileEditorWindow** (Client) — клиентские компоненты, использующие фабрику для создания редакторов

Взаимодействие компонентов Factory в проекте реализовано следующим образом:

### 1. Запрос на создание редактора → Client

Клиентский компонент (например, `EditorManager` или `FileEditorWindow`) получает запрос на открытие файла от пользователя или другого компонента системы. В методе `open_file()` класса `EditorManager` или в методе `on_display_content()` класса `FileEditorWindow` определяется необходимость создания нового редактора для отображения содержимого файла. Клиентский код не знает, какой именно редактор будет создан — он работает только с абстрактным интерфейсом `BaseFileEditor`.

### 2. Client → Factory (запрос на создание)

Клиентский компонент обращается к фабрике через статический метод `EditorFactory.create_editor()` или `EditorFactory.create_editor_for_type()`, передавая информацию о типе файла. В методе `_setup_editor_from_cache()` класса `EditorManager` выполняется вызов:

```python
editor = self.editor_factory.create_editor(file_path, parent_widget)
```

где `file_path` используется для извлечения расширения файла, а `parent_widget` передается конструктору редактора. Важно отметить, что клиентский код не содержит условных конструкций для выбора типа редактора — вся логика выбора инкапсулирована в фабрике.

### 3. Factory → определение типа продукта

Фабрика получает запрос и определяет, какой именно класс редактора должен быть создан. В методе `create_editor()` класса `EditorFactory` происходит:

- Извлечение расширения файла из пути (если передан полный путь) или использование переданного расширения напрямую
- Нормализация расширения (приведение к нижнему регистру) для обеспечения регистронезависимого сопоставления
- Поиск соответствующего класса в реестре `_registry` через метод `get()`
- Если класс найден — возврат ссылки на класс редактора
- Если класс не найден — возврат класса редактора по умолчанию (`PlainTextEditor`)

### 4. Factory → создание экземпляра ConcreteProduct

Фабрика создает экземпляр выбранного конкретного продукта, вызывая конструктор соответствующего класса с передачей необходимых параметров. В методе `create_editor()` после определения класса выполняется:

```python
return editor_class(parent=parent)
```

где `editor_class` является ссылкой на один из классов: `STEditor`, `MarkdownEditor` или `PlainTextEditor`. Конструктор конкретного редактора инициализирует специфичные для данного типа редактора компоненты: `STEditor` создает `QTextEdit` с `STHighlighter`, `MarkdownEditor` создает `MarkdownViewer` и настраивает разделенный интерфейс, `PlainTextEditor` инициализирует базовую функциональность.

### 5. Factory → возврат продукта клиенту

Фабрика возвращает созданный экземпляр редактора клиентскому коду. Важно, что возвращаемый объект имеет тип `BaseFileEditor`, что позволяет клиенту работать с ним через абстрактный интерфейс, не зная конкретного типа редактора. Это обеспечивает полиморфизм и слабую связанность между клиентом и конкретными реализациями.

### 6. Client → использование продукта

Клиентский код получает экземпляр редактора и использует его через абстрактный интерфейс `BaseFileEditor`. В методе `_setup_editor_from_cache()` класса `EditorManager` после получения редактора выполняются операции:

```python
editor.set_content(content)
self.current_editor = editor
self.editor_ready.emit(editor, file_path)
```

Клиент вызывает методы `set_content()`, `file_path`, работает со свойствами `is_modified`, подписывается на сигналы `modification_changed`, `undo_available`, `redo_available` — все эти операции выполняются через абстрактный интерфейс, без знания конкретного типа редактора. Полиморфизм обеспечивает, что вызов метода `set_content()` на `STEditor` выполнит одну логику (установка структурированного контента), а на `MarkdownEditor` — другую (установка Markdown-текста с последующим преобразованием).

### 7. Расширяемость через реестр

Важным аспектом реализации является возможность динамического расширения системы через регистрацию новых редакторов. Метод `register_editor()` класса `EditorFactory` позволяет добавлять поддержку новых типов файлов без изменения существующего кода фабрики или клиентских компонентов:

```python
EditorFactory.register_editor('.py', PythonEditor)
```

После регистрации фабрика автоматически начнет создавать экземпляры `PythonEditor` для файлов с расширением `.py`, при этом клиентский код не требует изменений, так как продолжает работать с абстрактным интерфейсом `BaseFileEditor`.

## Преимущества применения

Применение паттерна Factory в модуле редакторов обеспечивает следующие преимущества:

- **Инкапсуляция логики создания**: Вся логика выбора и создания конкретных редакторов сосредоточена в одном месте (`EditorFactory`), что упрощает понимание и поддержку кода. Изменения в процессе создания редакторов требуют модификации только фабрики, а не всех клиентских компонентов.

- **Слабая связанность**: Клиентский код не зависит от конкретных классов редакторов, а работает только с абстрактным интерфейсом `BaseFileEditor`. Это позволяет заменять реализации редакторов без изменения клиентского кода, что соответствует принципу инверсии зависимостей (Dependency Inversion Principle).

- **Расширяемость**: Добавление поддержки нового типа файлов требует только создания нового класса редактора (наследника `BaseFileEditor`) и его регистрации в фабрике через метод `register_editor()`. Существующий код не требует изменений, что обеспечивает открытость для расширения и закрытость для модификации (Open/Closed Principle).

- **Единообразие интерфейса**: Все редакторы предоставляют единый интерфейс через `BaseFileEditor`, что упрощает работу с ними в клиентском коде. Клиент может вызывать одни и те же методы (`load()`, `save()`, `get_content()`) независимо от конкретного типа редактора.

- **Централизованное управление**: Фабрика служит единой точкой управления созданием редакторов, что позволяет легко отслеживать, какие редакторы создаются, добавлять логирование, кэширование экземпляров или другие cross-cutting concerns без изменения клиентского кода.

- **Упрощение тестирования**: Клиентский код может быть протестирован с использованием mock-объектов, реализующих интерфейс `BaseFileEditor`, без необходимости создания реальных редакторов. Фабрика также может быть легко заменена на тестовую реализацию для изоляции тестов.

- **Обработка неизвестных типов**: Фабрика обеспечивает graceful degradation — для неподдерживаемых расширений автоматически возвращается редактор по умолчанию (`PlainTextEditor`), что гарантирует работоспособность системы даже при открытии файлов неизвестных типов.

Таким образом, реализация паттерна Factory в системе редакторов обеспечивает гибкость, расширяемость и поддерживаемость кода, что соответствует принципам современной разработки программного обеспечения и способствует созданию архитектуры, готовой к эволюции и развитию.
