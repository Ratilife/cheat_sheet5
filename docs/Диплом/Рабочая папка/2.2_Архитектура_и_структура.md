# 2.2. Архитектура и структура программного средства

## 2.2.1. Общее описание программного средства

Разработанное программное средство представляет собой кроссплатформенное десктопное приложение для организации, хранения и быстрого доступа к учебным материалам и фрагментам кода для IT-специалистов. Приложение предназначено для решения проблемы фрагментированного хранения учебных материалов и обеспечивает централизованный доступ к структурированной базе знаний.

Основное назначение программного средства заключается в предоставлении пользователю инструмента для:
- структурированного хранения фрагментов кода и учебных материалов;
- быстрого доступа к часто используемым приложениям и файлам через стартовую панель;
- создания и редактирования файлов в специализированных форматах (ST и Markdown);
- навигации по иерархической структуре учебных материалов;
- синтаксической подсветки кода различных языков программирования.

Программное средство реализовано как однопользовательское приложение с графическим интерфейсом, работающее в операционных системах Windows, Linux и macOS.

## 2.2.2. Архитектура приложения

### 2.2.2.1. Архитектурный стиль

Программное средство построено на основе многослойной модульной архитектуры (Layered Architecture), которая обеспечивает четкое разделение ответственности между компонентами системы. Выбор данного архитектурного стиля обусловлен следующими факторами:

1. **Масштабируемость**: модульная структура позволяет легко добавлять новые функциональные возможности без изменения существующего кода;
2. **Поддерживаемость**: четкое разделение на слои упрощает понимание структуры приложения и внесение изменений;
3. **Тестируемость**: изолированные модули могут быть протестированы независимо друг от друга;
4. **Переиспользование**: компоненты нижних слоев могут использоваться различными компонентами верхних слоев.

### 2.2.2.2. Структура слоев приложения

Архитектура приложения состоит из четырех основных слоев (рисунок 2.1):

**Слой представления (Presentation Layer)**
- Компоненты: `src/ui/`, `src/start_panel/views/`, `src/widgets/`
- Назначение: отображение пользовательского интерфейса, обработка пользовательских действий
- Технологии: PySide6 (Qt6), виджеты Qt Designer

**Слой бизнес-логики (Business Logic Layer)**
- Компоненты: `src/managers/`, `src/controllers/`, `src/editor/`, `src/dialogs/`
- Назначение: реализация бизнес-правил, координация работы компонентов, управление состоянием приложения
- Основные компоненты:
  - `EditorManager` — управление редакторами файлов
  - `TreeModelManager` — управление моделями дерева файлов
  - `FileManager` — управление файловыми операциями
  - `UIManager` — координация пользовательского интерфейса

**Слой доступа к данным (Data Access Layer)**
- Компоненты: `src/models/`, `src/parsers/`, `src/operation/`
- Назначение: работа с данными, парсинг файлов, кэширование, операции с файлами
- Основные компоненты:
  - `STMDFileTreeModel` — модель данных для отображения дерева файлов
  - `FileParserService` — сервис парсинга ST и MD файлов
  - `ContentCache` — кэш полного содержимого файлов
  - `MetadataCache` — кэш метаданных файлов

**Инфраструктурный слой (Infrastructure Layer)**
- Компоненты: `src/utils/`, `src/observers/`, `src/global_var/`, `src/ANTLR4/`
- Назначение: вспомогательные утилиты, наблюдение за изменениями, конфигурация, грамматики парсинга
- Основные компоненты:
  - `FileWatcher` — отслеживание изменений файлов
  - `Config` — управление конфигурацией приложения
  - Грамматики ANTLR4 для различных языков программирования

### 2.2.2.3. Используемые паттерны проектирования

В архитектуре приложения применены следующие паттерны проектирования:

**1. Паттерн Model-View-ViewModel (MVVM)**
- Применение: модуль стартовой панели (`src/start_panel/`)
- Структура:
  - Model (`ButtonListModel`) — управление данными о кнопках
  - View (`MainWindow`, `ViewDeleteButtons`) — отображение интерфейса
  - ViewModel (`ButtonViewModel`, `ViewModelDeleteButtons`) — связь между Model и View
- Преимущества: разделение логики и представления, упрощение тестирования

**2. Паттерн Factory (Фабрика)**
- Применение: создание редакторов файлов (`EditorFactory`)
- Назначение: создание объектов редакторов в зависимости от типа файла (ST, MD, Plain Text)
- Преимущества: инкапсуляция логики создания объектов, расширяемость

**3. Паттерн Observer (Наблюдатель)**
- Применение: отслеживание изменений файлов (`FileWatcher`, `MyBaseObserver`)
- Назначение: автоматическое обновление интерфейса при изменении файлов на диске
- Преимущества: слабая связанность компонентов, реактивность системы

**4. Паттерн Singleton (Одиночка)**
- Применение: кэши (`ContentCache`, `MetadataCache`)
- Назначение: обеспечение единственного экземпляра кэша во всем приложении
- Преимущества: централизованное управление кэшем, экономия памяти

**5. Паттерн Strategy (Стратегия)**
- Применение: различные типы редакторов (`BaseFileEditor`, `STEditor`, `MarkdownEditor`)
- Назначение: инкапсуляция алгоритмов редактирования для разных типов файлов
- Преимущества: возможность динамического выбора алгоритма, расширяемость

## 2.2.3. Структура данных и хранение информации

### 2.2.3.1. Общая схема хранения данных

Программное средство использует файловую систему для хранения данных. База данных не применяется, что упрощает развертывание и обеспечивает прямую доступность файлов пользователю. Структура хранения данных организована следующим образом:

```
cheat_sheet/                          # Корневая папка проекта
├── for_program/                      # Служебные файлы приложения
│   ├── buttons.json                  # Конфигурация кнопок стартовой панели
│   └── saved_files.json             # Реестр внешних файлов
└── bookmarks/                        # Рабочие файлы пользователя
    ├── 1C/                          # Вкладка "1C"
    ├── Csharp/                      # Вкладка "C#"
    ├── java/                        # Вкладка "Java"
    └── python/                      # Вкладка "Python"
```

Конфигурация корневой папки хранится в файле `root_folder_path.json` в домашней директории пользователя.

### 2.2.3.2. Описание форматов данных

**1. Файл конфигурации кнопок (`buttons.json`)**

Файл содержит массив объектов, каждый из которых представляет пользовательскую кнопку стартовой панели:

```json
[
    {
        "name": "Notepad++",
        "path": "\"C:\\Program Files\\Notepad++\\notepad++.exe\""
    },
    {
        "name": "VSCode",
        "path": "\"E:\\Program Files\\Microsoft VS Code\\Code.exe\""
    }
]
```

Структура объекта:
- `name` (string) — отображаемое имя кнопки
- `path` (string) — путь к приложению или файлу (с экранированием кавычек для путей с пробелами)

**2. Реестр внешних файлов (`saved_files.json`)**

Файл содержит массив объектов, описывающих файлы, расположенные вне корневой папки проекта:

```json
[
    {
        "path": "F:/Projects/example.st",
        "type": "file",
        "tab_name": "1C"
    },
    {
        "path": "E:/Documents/guide.md",
        "type": "markdown",
        "tab_name": "Python"
    }
]
```

Структура объекта:
- `path` (string) — полный путь к файлу
- `type` (string) — тип содержимого: `"file"` для ST-файлов, `"markdown"` для MD-файлов
- `tab_name` (string) — имя вкладки для отображения в интерфейсе

**3. Конфигурация корневой папки (`root_folder_path.json`)**

Файл хранится в домашней директории пользователя и содержит информацию о корневой папке проекта:

```json
{
    "path": "F:/Языки/Python/Partfolio/cheat_sheet5/cheat_sheet",
    "date": "01-09-2025"
}
```

Структура объекта:
- `path` (string) — путь к корневой папке проекта
- `date` (string) — дата последнего обновления в формате DD-MM-YYYY

### 2.2.3.3. Модели данных приложения

**1. Модель дерева файлов (`STMDFileTreeModel`)**

Модель наследуется от `QAbstractItemModel` и представляет иерархическую структуру файлов для отображения в Qt TreeView. Элементы модели представлены классом `STMDFileTreeItem`, который содержит:

- `name` — имя элемента
- `type` — тип элемента (`file`, `folder`, `template`, `markdown`)
- `file_path` — путь к файлу (для файлов и шаблонов)
- `parent_item` — ссылка на родительский элемент
- `child_items` — список дочерних элементов

**2. Модель кнопок стартовой панели (`ButtonListModel`)**

Модель управляет списком кнопок стартовой панели. Основной элемент данных — `ButtonModel` (dataclass):

```python
@dataclass
class ButtonModel:
    name: str   # Название кнопки
    path: str   # Путь к программе
```

**3. Структура данных парсинга**

Результат парсинга ST-файла представляет собой словарь:

```python
{
    'root_name': str,           # Имя корневого элемента
    'structure': [              # Список элементов структуры
        {
            'name': str,        # Имя элемента
            'type': str,        # Тип: 'folder', 'template'
            'flags': int,       # Флаги элемента
            'desc1': str,       # Описание 1
            'desc2': str,       # Описание 2
            'content': str,     # Содержимое (для шаблонов)
            'children': [...]   # Дочерние элементы
        }
    ]
}
```

Результат парсинга MD-файла имеет аналогичную структуру, но адаптированную для Markdown-разметки.

### 2.2.3.4. Система кэширования

Для оптимизации производительности приложение использует двухуровневую систему кэширования:

**1. Кэш метаданных (`MetadataCache`)**
- Назначение: хранение легковесных метаданных (структура дерева, имена элементов)
- Алгоритм: TTL (Time To Live) с автоматической инвалидацией при изменении файла
- Время жизни по умолчанию: 300 секунд (5 минут)
- Проверка актуальности: сравнение размера файла и времени модификации

**2. Кэш содержимого (`ContentCache`)**
- Назначение: хранение полного содержимого распарсенных файлов
- Алгоритм: LRU (Least Recently Used) с ограничением по размеру
- Максимальный размер: 100 МБ по умолчанию
- Потокобезопасность: использование `threading.RLock()` для синхронизации

Оба кэша реализованы как Singleton для обеспечения единого экземпляра во всем приложении.

## 2.2.4. Взаимодействие компонентов системы

### 2.2.4.1. Поток обработки открытия файла

Процесс открытия файла пользователем включает следующие этапы:

1. **Пользовательский ввод**: пользователь выбирает файл в дереве файлов
2. **Обработка события**: `TreeSelectionController` обрабатывает событие выбора
3. **Запрос редактора**: контроллер отправляет запрос в `EditorManager`
4. **Проверка кэша**: `EditorManager` проверяет наличие данных в `ContentCache`
5. **Создание редактора**: `EditorFactory` создает соответствующий редактор (ST/MD/Plain Text)
6. **Загрузка данных**:
   - Если данные в кэше — загрузка из кэша (мгновенно)
   - Если данных нет — запуск фонового парсинга через `BackgroundParser`
7. **Отображение**: редактор отображается в интерфейсе с данными из кэша или превью из `MetadataCache`
8. **Обновление**: при завершении парсинга редактор обновляется полными данными

### 2.2.4.2. Поток парсинга файла

Процесс парсинга файла выполняется следующим образом:

1. **Инициализация**: `FileParserService` определяет тип файла по расширению
2. **Выбор парсера**:
   - Для `.st` файлов — `STFileParserWrapper` с использованием ANTLR4 грамматики
   - Для `.md` файлов — `MarkdownListener` для парсинга Markdown
3. **Парсинг**: парсер обрабатывает файл и извлекает структурированные данные
4. **Кэширование метаданных**: легковесные метаданные сохраняются в `MetadataCache`
5. **Кэширование содержимого**: полные данные сохраняются в `ContentCache`
6. **Уведомление**: через сигналы Qt уведомляются заинтересованные компоненты об обновлении

### 2.2.4.3. Поток создания кнопки в стартовой панели

Процесс создания пользовательской кнопки (MVVM паттерн):

1. **Пользовательский ввод**: пользователь нажимает кнопку "Создать кнопку"
2. **View**: `MainWindow` открывает диалоговое окно для ввода данных
3. **ViewModel**: `ButtonViewModel` получает данные от View
4. **Валидация**: ViewModel проверяет уникальность имени кнопки
5. **Обновление Model**: `ButtonListModel` добавляет новую кнопку в список
6. **Сохранение**: Model сохраняет данные в `buttons.json`
7. **Обновление View**: ViewModel уведомляет View об изменении, View обновляет интерфейс

### 2.2.4.4. Система наблюдения за файлами

Компонент `FileWatcher` отслеживает изменения файлов на диске:

1. **Регистрация**: при открытии файла он регистрируется в `FileWatcher`
2. **Мониторинг**: система отслеживает изменения через механизмы операционной системы
3. **Обнаружение изменения**: при изменении файла генерируется событие
4. **Инвалидация кэша**: соответствующие записи удаляются из `ContentCache` и `MetadataCache`
5. **Уведомление UI**: через сигналы Qt уведомляются компоненты интерфейса
6. **Обновление**: модели дерева и редакторы обновляются с новыми данными

## 2.2.6. Структура модулей приложения

### 2.2.6.1. Основные модули

**Модуль `src/ANTLR4/`**
- Назначение: грамматики ANTLR4 для парсинга различных языков программирования
- Подмодули:
  - `st_grammar/` — грамматика для Structured Text файлов
  - `one_c_grammar/` — грамматики для языка 1C (BSL, SDBL)
  - `py_grammar/` — грамматика для Python
  - `java_grammar/` — грамматика для Java
  - `ch_grammar/` — грамматика для C#
- Структура каждого подмодуля:
  - `.g4` файлы — определения грамматик
  - Сгенерированные файлы: `*Lexer.py`, `*Parser.py`, `*Listener.py`

**Модуль `src/parsers/`**
- Назначение: парсинг файлов и управление кэшированием
- Основные компоненты:
  - `file_parser_service.py` — сервис парсинга, координатор парсеров
  - `st_file_parser.py` — парсер ST-файлов
  - `md_file_parser.py` — парсер Markdown-файлов
  - `content_cache.py` — кэш полного содержимого (LRU)
  - `metadata_cache.py` — кэш метаданных (TTL)
  - `background_parser.py` — фоновый парсинг для оптимизации

**Модуль `src/editor/`**
- Назначение: система редакторов для различных типов файлов
- Основные компоненты:
  - `base_editor.py` — абстрактный базовый класс редактора
  - `st_editor.py` — редактор ST-файлов с иерархическим представлением
  - `markdown_editor.py` — редактор Markdown с предпросмотром
  - `plain_text_editor.py` — простой текстовый редактор
  - `editor_factory.py` — фабрика для создания редакторов
  - `editor_manager.py` — менеджер редакторов, координатор работы

**Модуль `src/managers/`**
- Назначение: менеджеры для координации работы различных подсистем
- Основные компоненты:
  - `tree_model_manager.py` — управление моделями дерева файлов
  - `file_manager.py` — управление файловыми операциями
  - `ui_manager.py` — координация пользовательского интерфейса
  - `toolbar_manager.py` — управление панелями инструментов
  - `dynamic_tabs.py` — управление динамическими вкладками

**Модуль `src/models/`**
- Назначение: модели данных для представления структуры приложения
- Основные компоненты:
  - `st_md_file_tree_model.py` — модель дерева файлов для Qt
  - `st_md_file_tree_item.py` — элемент дерева файлов

**Модуль `src/start_panel/`**
- Назначение: стартовая панель приложения (реализация MVVM)
- Структура:
  - `models/model.py` — модель данных кнопок
  - `view_models/` — ViewModel компоненты
  - `views/` — View компоненты (окна)

**Модуль `src/ui/`**
- Назначение: пользовательский интерфейс, созданный в Qt Designer
- Компоненты: UI-файлы и их Python-обертки

**Модуль `src/utils/`**
- Назначение: вспомогательные утилиты
- Компоненты:
  - `cache_manager.py` — управление кэшами
  - `clipboard_manager.py` — работа с буфером обмена
  - `delta_processor.py` — обработка изменений (delta operations)

**Модуль `src/observers/`**
- Назначение: система наблюдения за изменениями
- Компоненты:
  - `file_watcher.py` — отслеживание изменений файлов
  - `my_base_observer.py` — базовый класс наблюдателя

**Модуль `src/controllers/`**
- Назначение: контроллеры для обработки пользовательских действий
- Компоненты:
  - `selection_controller.py` — контроллер выделения в дереве файлов

**Модуль `src/operation/`**
- Назначение: операции с файлами и данными
- Компоненты:
  - `file_operations.py` — файловые операции
  - `delta_operations.py` — операции с изменениями (delta)

**Модуль `src/global_var/`**
- Назначение: глобальные переменные и конфигурация
- Компоненты:
  - `config.py` — управление конфигурацией приложения

### 2.2.6.2. Точка входа приложения

Файл `main.py` является точкой входа приложения и выполняет следующие функции:

1. Инициализация Qt-приложения (`QApplication`)
2. Загрузка конфигурации через `config.load_config()`
3. Создание модели данных (`ButtonListModel`)
4. Создание ViewModel (`ButtonViewModel`)
5. Создание главного окна (`MainWindow`)
6. Запуск главного цикла приложения (`app.exec()`)

## 2.2.7. Заключение по разделу

В данном разделе представлена архитектура и структура разработанного программного средства. Приложение построено на основе многослойной модульной архитектуры, что обеспечивает четкое разделение ответственности между компонентами и упрощает поддержку и развитие системы.

Ключевые особенности архитектуры:
- Использование паттернов проектирования (MVVM, Factory, Observer, Singleton, Strategy) для обеспечения гибкости и расширяемости
- Двухуровневая система кэширования для оптимизации производительности
- Фоновый парсинг для обеспечения отзывчивости интерфейса
- Файловая система хранения данных для упрощения развертывания
- Кроссплатформенность благодаря использованию Python и Qt6

Структура приложения организована в виде модулей с четко определенными обязанностями, что соответствует принципам SOLID и обеспечивает возможность независимого тестирования и развития отдельных компонентов системы.
