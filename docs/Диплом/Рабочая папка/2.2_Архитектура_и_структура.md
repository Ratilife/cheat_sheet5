# 2.2. Архитектура и структура программного средства

## 2.2.1. Общее описание программного средства

Разработанное программное средство представляет собой кроссплатформенное десктопное приложение для организации, хранения и быстрого доступа к учебным материалам и фрагментам кода для IT-специалистов. Приложение предназначено для решения проблемы фрагментированного хранения учебных материалов и обеспечивает централизованный доступ к структурированной базе знаний.

Основное назначение программного средства заключается в предоставлении пользователю инструмента для:
- структурированного хранения фрагментов кода и учебных материалов;
- быстрого доступа к часто используемым приложениям и файлам через стартовую панель;
- создания и редактирования файлов в специализированных форматах (ST и Markdown);
- навигации по иерархической структуре учебных материалов;
- синтаксической подсветки кода различных языков программирования.

Программное средство реализовано как однопользовательское приложение с графическим интерфейсом, работающее в операционных системах Windows, Linux и macOS.

## 2.2.2. Архитектура приложения

### 2.2.2.1. Архитектурный стиль

Программное средство построено на основе многослойной модульной архитектуры (Layered Architecture), которая обеспечивает четкое разделение ответственности между компонентами системы. Выбор данного архитектурного стиля обусловлен следующими факторами:

1. **Масштабируемость**: модульная структура позволяет легко добавлять новые функциональные возможности без изменения существующего кода;
2. **Поддерживаемость**: четкое разделение на слои упрощает понимание структуры приложения и внесение изменений;
3. **Тестируемость**: изолированные модули могут быть протестированы независимо друг от друга;
4. **Переиспользование**: компоненты нижних слоев могут использоваться различными компонентами верхних слоев.

### 2.2.2.2. Структура слоев приложения

Архитектура приложения состоит из четырех основных слоев (рисунок 2.1):

**Слой представления (Presentation Layer)**
- Компоненты: `src/ui/`, `src/start_panel/views/`, `src/widgets/`
- Назначение: отображение пользовательского интерфейса, обработка пользовательских действий
- Технологии: PySide6 (Qt6), виджеты Qt Designer

**Слой бизнес-логики (Business Logic Layer)**
- Компоненты: `src/managers/`, `src/controllers/`, `src/editor/`, `src/dialogs/`
- Назначение: реализация бизнес-правил, координация работы компонентов, управление состоянием приложения
- Основные компоненты:
  - `EditorManager` — управление редакторами файлов
  - `TreeModelManager` — управление моделями дерева файлов
  - `FileManager` — управление файловыми операциями
  - `UIManager` — координация пользовательского интерфейса

**Слой доступа к данным (Data Access Layer)**
- Компоненты: `src/models/`, `src/parsers/`, `src/operation/`
- Назначение: работа с данными, парсинг файлов, кэширование, операции с файлами
- Основные компоненты:
  - `STMDFileTreeModel` — модель данных для отображения дерева файлов
  - `FileParserService` — сервис парсинга ST и MD файлов
  - `ContentCache` — кэш полного содержимого файлов
  - `MetadataCache` — кэш метаданных файлов

**Инфраструктурный слой (Infrastructure Layer)**
- Компоненты: `src/utils/`, `src/observers/`, `src/global_var/`, `src/ANTLR4/`
- Назначение: вспомогательные утилиты, наблюдение за изменениями, конфигурация, грамматики парсинга
- Основные компоненты:
  - `FileWatcher` — отслеживание изменений файлов
  - `Config` — управление конфигурацией приложения
  - Грамматики ANTLR4 для различных языков программирования

### 2.2.2.3. Используемые паттерны проектирования

В архитектуре приложения применены следующие паттерны проектирования:

**1. Паттерн Model-View-ViewModel (MVVM)**
- Применение: модуль стартовой панели (`src/start_panel/`)
- Структура:
  - Model (`ButtonListModel`) — управление данными о кнопках
  - View (`MainWindow`, `ViewDeleteButtons`) — отображение интерфейса
  - ViewModel (`ButtonViewModel`, `ViewModelDeleteButtons`) — связь между Model и View
- Преимущества: разделение логики и представления, упрощение тестирования

**2. Паттерн Factory (Фабрика)**
- Применение: создание редакторов файлов (`EditorFactory`)
- Назначение: создание объектов редакторов в зависимости от типа файла (ST, MD, Plain Text)
- Преимущества: инкапсуляция логики создания объектов, расширяемость

**3. Паттерн Observer (Наблюдатель)**
- Применение: отслеживание изменений файлов (`FileWatcher`, `MyBaseObserver`)
- Назначение: автоматическое обновление интерфейса при изменении файлов на диске
- Преимущества: слабая связанность компонентов, реактивность системы

**4. Паттерн Singleton (Одиночка)**
- Применение: кэши (`ContentCache`, `MetadataCache`)
- Назначение: обеспечение единственного экземпляра кэша во всем приложении
- Преимущества: централизованное управление кэшем, экономия памяти

**5. Паттерн Strategy (Стратегия)**
- Применение: различные типы редакторов (`BaseFileEditor`, `STEditor`, `MarkdownEditor`)
- Назначение: инкапсуляция алгоритмов редактирования для разных типов файлов
- Преимущества: возможность динамического выбора алгоритма, расширяемость

## 2.2.3. Структура данных и хранение информации

### 2.2.3.1. Общая схема хранения данных

Программное средство использует файловую систему для хранения данных. База данных не применяется, что упрощает развертывание и обеспечивает прямую доступность файлов пользователю. Структура хранения данных организована следующим образом:

```
cheat_sheet/                          # Корневая папка проекта
├── for_program/                      # Служебные файлы приложения
│   ├── buttons.json                  # Конфигурация кнопок стартовой панели
│   └── saved_files.json             # Реестр внешних файлов
└── bookmarks/                        # Рабочие файлы пользователя
    ├── 1C/                          # Вкладка "1C"
    ├── Csharp/                      # Вкладка "C#"
    ├── java/                        # Вкладка "Java"
    └── python/                      # Вкладка "Python"
```

Конфигурация корневой папки хранится в файле `root_folder_path.json` в домашней директории пользователя.

### 2.2.3.2. Описание форматов данных

**1. Файл конфигурации кнопок (`buttons.json`)**

Файл содержит массив объектов, каждый из которых представляет пользовательскую кнопку стартовой панели:

```json
[
    {
        "name": "Notepad++",
        "path": "\"C:\\Program Files\\Notepad++\\notepad++.exe\""
    },
    {
        "name": "VSCode",
        "path": "\"E:\\Program Files\\Microsoft VS Code\\Code.exe\""
    }
]
```

Структура объекта:
- `name` (string) — отображаемое имя кнопки
- `path` (string) — путь к приложению или файлу (с экранированием кавычек для путей с пробелами)

**2. Реестр внешних файлов (`saved_files.json`)**

Файл содержит массив объектов, описывающих файлы, расположенные вне корневой папки проекта:

```json
[
    {
        "path": "F:/Projects/example.st",
        "type": "file",
        "tab_name": "1C"
    },
    {
        "path": "E:/Documents/guide.md",
        "type": "markdown",
        "tab_name": "Python"
    }
]
```

Структура объекта:
- `path` (string) — полный путь к файлу
- `type` (string) — тип содержимого: `"file"` для ST-файлов, `"markdown"` для MD-файлов
- `tab_name` (string) — имя вкладки для отображения в интерфейсе

**3. Конфигурация корневой папки (`root_folder_path.json`)**

Файл хранится в домашней директории пользователя и содержит информацию о корневой папке проекта:

```json
{
    "path": "F:/Языки/Python/Partfolio/cheat_sheet5/cheat_sheet",
    "date": "01-09-2025"
}
```

Структура объекта:
- `path` (string) — путь к корневой папке проекта
- `date` (string) — дата последнего обновления в формате DD-MM-YYYY

### 2.2.3.3. Модели данных приложения

**1. Модель дерева файлов (`STMDFileTreeModel`)**

Модель наследуется от `QAbstractItemModel` и представляет иерархическую структуру файлов для отображения в Qt TreeView. Элементы модели представлены классом `STMDFileTreeItem`, который содержит:

- `name` — имя элемента
- `type` — тип элемента (`file`, `folder`, `template`, `markdown`)
- `file_path` — путь к файлу (для файлов и шаблонов)
- `parent_item` — ссылка на родительский элемент
- `child_items` — список дочерних элементов

**2. Модель кнопок стартовой панели (`ButtonListModel`)**

Модель управляет списком кнопок стартовой панели. Основной элемент данных — `ButtonModel` (dataclass):

```python
@dataclass
class ButtonModel:
    name: str   # Название кнопки
    path: str   # Путь к программе
```

**3. Структура данных парсинга**

Результат парсинга ST-файла представляет собой словарь:

```python
{
    'root_name': str,           # Имя корневого элемента
    'structure': [              # Список элементов структуры
        {
            'name': str,        # Имя элемента
            'type': str,        # Тип: 'folder', 'template'
            'flags': int,       # Флаги элемента
            'desc1': str,       # Описание 1
            'desc2': str,       # Описание 2
            'content': str,     # Содержимое (для шаблонов)
            'children': [...]   # Дочерние элементы
        }
    ]
}
```

Результат парсинга MD-файла имеет аналогичную структуру, но адаптированную для Markdown-разметки.

### 2.2.3.4. Система кэширования

Для оптимизации производительности приложение использует двухуровневую систему кэширования:

**1. Кэш метаданных (`MetadataCache`)**
- Назначение: хранение легковесных метаданных (структура дерева, имена элементов)
- Алгоритм: TTL (Time To Live) с автоматической инвалидацией при изменении файла
- Время жизни по умолчанию: 300 секунд (5 минут)
- Проверка актуальности: сравнение размера файла и времени модификации

**2. Кэш содержимого (`ContentCache`)**
- Назначение: хранение полного содержимого распарсенных файлов
- Алгоритм: LRU (Least Recently Used) с ограничением по размеру
- Максимальный размер: 100 МБ по умолчанию
- Потокобезопасность: использование `threading.RLock()` для синхронизации

Оба кэша реализованы как Singleton для обеспечения единого экземпляра во всем приложении.

## 2.2.4. Взаимодействие компонентов системы

### 2.2.4.1. Поток обработки открытия файла

Процесс открытия файла пользователем включает следующие этапы:

1. **Пользовательский ввод**: пользователь выбирает файл в дереве файлов
2. **Обработка события**: `TreeSelectionController` обрабатывает событие выбора
3. **Запрос редактора**: контроллер отправляет запрос в `EditorManager`
4. **Проверка кэша**: `EditorManager` проверяет наличие данных в `ContentCache`
5. **Создание редактора**: `EditorFactory` создает соответствующий редактор (ST/MD/Plain Text)
6. **Загрузка данных**:
   - Если данные в кэше — загрузка из кэша (мгновенно)
   - Если данных нет — запуск фонового парсинга через `BackgroundParser`
7. **Отображение**: редактор отображается в интерфейсе с данными из кэша или превью из `MetadataCache`
8. **Обновление**: при завершении парсинга редактор обновляется полными данными

### 2.2.4.2. Поток парсинга файла

Процесс парсинга файла выполняется следующим образом:

1. **Инициализация**: `FileParserService` определяет тип файла по расширению
2. **Выбор парсера**:
   - Для `.st` файлов — `STFileParserWrapper` с использованием ANTLR4 грамматики
   - Для `.md` файлов — `MarkdownListener` для парсинга Markdown
3. **Парсинг**: парсер обрабатывает файл и извлекает структурированные данные
4. **Кэширование метаданных**: легковесные метаданные сохраняются в `MetadataCache`
5. **Кэширование содержимого**: полные данные сохраняются в `ContentCache`
6. **Уведомление**: через сигналы Qt уведомляются заинтересованные компоненты об обновлении

### 2.2.4.3. Поток создания кнопки в стартовой панели

Процесс создания пользовательской кнопки (MVVM паттерн):

1. **Пользовательский ввод**: пользователь нажимает кнопку "Создать кнопку"
2. **View**: `MainWindow` открывает диалоговое окно для ввода данных
3. **ViewModel**: `ButtonViewModel` получает данные от View
4. **Валидация**: ViewModel проверяет уникальность имени кнопки
5. **Обновление Model**: `ButtonListModel` добавляет новую кнопку в список
6. **Сохранение**: Model сохраняет данные в `buttons.json`
7. **Обновление View**: ViewModel уведомляет View об изменении, View обновляет интерфейс

### 2.2.4.4. Система наблюдения за файлами

Компонент `FileWatcher` отслеживает изменения файлов на диске:

1. **Регистрация**: при открытии файла он регистрируется в `FileWatcher`
2. **Мониторинг**: система отслеживает изменения через механизмы операционной системы
3. **Обнаружение изменения**: при изменении файла генерируется событие
4. **Инвалидация кэша**: соответствующие записи удаляются из `ContentCache` и `MetadataCache`
5. **Уведомление UI**: через сигналы Qt уведомляются компоненты интерфейса
6. **Обновление**: модели дерева и редакторы обновляются с новыми данными

### 2.2.4.5. Механизм взаимодействия компонентов

Взаимодействие компонентов программного средства организовано на основе нескольких ключевых механизмов, обеспечивающих слабую связанность, реактивность и расширяемость системы.

#### 2.2.4.5.1. Архитектурные принципы взаимодействия

Взаимодействие между компонентами системы базируется на следующих принципах:

**1. Разделение ответственности по слоям**

Компоненты организованы в четыре архитектурных слоя, каждый из которых имеет четко определенную роль:

- **Слой представления** взаимодействует с пользователем и передает команды в слой бизнес-логики через контроллеры и менеджеры
- **Слой бизнес-логики** координирует работу компонентов, обрабатывает команды и делегирует операции слою доступа к данным
- **Слой доступа к данным** выполняет операции с данными и уведомляет верхние слои об изменениях через механизм сигналов
- **Инфраструктурный слой** предоставляет сервисы (наблюдение, кэширование, конфигурация) всем остальным слоям

**2. Односторонний поток данных**

Взаимодействие между слоями организовано по принципу одностороннего потока данных:

- **Нисходящий поток (команды)**: View → ViewModel/Controller → Manager → Service → Model/Data
- **Восходящий поток (уведомления)**: Model/Data → Service → Manager → ViewModel → View (через сигналы Qt)

Такая организация предотвращает циклические зависимости и обеспечивает предсказуемость поведения системы.

**3. Слабая связанность через интерфейсы**

Компоненты взаимодействуют через абстрактные интерфейсы (`IButtonModel`, `IButtonViewModel`), что позволяет:

- Заменять реализации без изменения зависимых компонентов
- Легко тестировать компоненты с использованием mock-объектов
- Расширять функциональность через добавление новых реализаций интерфейсов

#### 2.2.4.5.2. Механизмы коммуникации

В системе используются три основных механизма коммуникации между компонентами:

**1. Сигналы и слоты Qt (Signal-Slot)**

Механизм сигналов и слотов Qt является основным средством асинхронной коммуникации между компонентами. Преимущества данного подхода:

- **Асинхронность**: сигналы обрабатываются в цикле событий Qt, не блокируя выполнение
- **Слабая связанность**: отправитель сигнала не знает о получателях
- **Типобезопасность**: сигналы имеют строго определенные типы параметров
- **Множественная подписка**: несколько компонентов могут подписаться на один сигнал

Примеры использования сигналов в системе:

- `EditorManager.editor_ready` — уведомление о готовности редактора
- `FileWatcher.file_updated` — уведомление об изменении файла
- `TreeModelManager.model_updated` — уведомление об обновлении модели дерева
- `ButtonViewModel.buttonsChanged` — уведомление об изменении списка кнопок

**2. Прямые вызовы методов**

Для синхронных операций, требующих немедленного результата, используются прямые вызовы методов:

- Запрос данных из кэша: `content_cache.get(file_path)`
- Создание редактора: `editor_factory.create_editor(file_path)`
- Валидация данных: `view_model.is_valid_button(name, path)`

Прямые вызовы применяются в случаях, когда:
- Операция должна быть выполнена синхронно
- Требуется немедленный результат для принятия решения
- Взаимодействие происходит внутри одного слоя

**3. Паттерн Observer через FileWatcher**

Компонент `FileWatcher` реализует паттерн Observer для отслеживания изменений файловой системы:

- **Subject (Наблюдаемый)**: `FileWatcher` отслеживает изменения файлов
- **Observers (Наблюдатели)**: редакторы (`STEditor`, `MarkdownEditor`), `SidePanel`, `TreeModelManager`

Механизм работы:

1. Компонент регистрируется в `FileWatcher` через метод `watch_file()` или `watch_directory()`
2. При изменении файла `FileWatcher` генерирует сигнал `file_updated` или `debounced_file_updated`
3. Подписанные компоненты получают уведомление и обновляют свое состояние
4. Для предотвращения частых обновлений используется дебаунсинг (задержка 300 мс)

#### 2.2.4.5.3. Координация работы менеджеров

Менеджеры (`EditorManager`, `TreeModelManager`, `FileManager`, `UIManager`) играют роль координаторов, обеспечивающих согласованную работу компонентов:

**1. EditorManager — координатор редакторов**

`EditorManager` координирует работу системы редакторов:

- **Интеграция с кэшем**: проверяет наличие данных в `ContentCache` перед парсингом
- **Управление жизненным циклом**: создает редакторы через `EditorFactory`, управляет их состоянием
- **Координация парсинга**: запускает фоновый парсинг через `BackgroundParser` при отсутствии данных в кэше
- **Уведомление компонентов**: испускает сигналы `editor_ready`, `loading_started`, `loading_finished`

**2. TreeModelManager — координатор моделей дерева**

`TreeModelManager` обеспечивает синхронизацию между файловой системой, кэшем и моделью дерева:

- **Синхронизация с парсером**: использует `FileParserService` для получения структуры файлов
- **Управление кэшем**: обновляет `ContentCache` и `MetadataCache` при изменениях
- **Координация с редакторами**: уведомляет редакторы об изменениях через сигналы
- **Интеграция с FileWatcher**: реагирует на изменения файлов, обнаруженные `FileWatcher`

**3. UIManager — координатор интерфейса**

`UIManager` обеспечивает единообразное создание элементов интерфейса:

- **Шаблонное создание**: предоставляет методы для создания кнопок, панелей инструментов
- **Централизованное управление**: хранит ссылки на созданные элементы для последующего доступа
- **Стандартизация**: обеспечивает единый стиль и поведение элементов интерфейса

#### 2.2.4.5.4. Система кэширования и синхронизация данных

Двухуровневая система кэширования требует механизмов синхронизации для обеспечения консистентности данных:

**1. Инвалидация кэша**

При изменении файла выполняется следующая последовательность действий:

1. `FileWatcher` обнаруживает изменение и испускает сигнал `file_updated`
2. Компоненты, подписанные на сигнал, инвалидируют соответствующие записи в кэше:
   - `ContentCache.remove(file_path)` — удаление полного содержимого
   - `MetadataCache.remove(file_path)` — удаление метаданных
3. При следующем обращении к файлу выполняется повторный парсинг

**2. Синхронизация между кэшами**

`MetadataCache` и `ContentCache` синхронизируются следующим образом:

- При парсинге файла сначала сохраняются метаданные в `MetadataCache`
- Затем полное содержимое сохраняется в `ContentCache`
- При инвалидации оба кэша очищаются одновременно
- `MetadataCache` используется для быстрого отображения превью, `ContentCache` — для полного содержимого

**3. Фоновый парсинг и обновление UI**

`BackgroundParser` обеспечивает асинхронный парсинг без блокировки интерфейса:

1. `EditorManager` запускает задачу парсинга через `BackgroundParser.add_task()`
2. Парсинг выполняется в фоновом потоке
3. По завершении парсинга результат сохраняется в кэш
4. Через сигнал `task_finished` уведомляются заинтересованные компоненты
5. Редактор обновляется с полными данными из кэша

#### 2.2.4.5.5. Паттерн MVVM в стартовой панели

Стартовая панель приложения реализует паттерн проектирования Model-View-ViewModel (MVVM), который обеспечивает четкое разделение ответственности между компонентами и упрощает тестирование и поддержку кода. Данный паттерн был выбран для реализации стартовой панели в связи с необходимостью управления динамическим списком пользовательских кнопок и обеспечения реактивного обновления интерфейса при изменении данных.

**Архитектура компонентов MVVM:**

В реализации паттерна MVVM выделяются три основных компонента:

- **Model** (`ButtonListModel`) — управляет данными о кнопках, обеспечивает бизнес-логику (валидация, проверка уникальности имен), выполняет персистентность данных в JSON-файл
- **ViewModel** (`ButtonViewModel`) — предоставляет абстракцию данных для View, преобразует команды пользователя в операции с Model, управляет состоянием представления
- **View** (`MainWindow`) — отвечает исключительно за отображение интерфейса и обработку пользовательских действий, не содержит бизнес-логики

**Механизм взаимодействия компонентов:**

Взаимодействие компонентов MVVM в проекте реализовано следующим образом:

**1. Пользовательское действие → View**

Пользователь выполняет действие в интерфейсе, например, нажимает кнопку "Добавить" в главном окне приложения. Событие обрабатывается методом `add_button_clicked()` класса `MainWindow`, который является частью слоя View. Данный метод отображает диалоговые окна для ввода пользователем названия кнопки и пути к программе через `QInputDialog.getText()`. После получения данных от пользователя View готов передать их в слой ViewModel.

**2. View → ViewModel (делегирование команды)**

View вызывает соответствующий метод ViewModel, передавая полученные от пользователя данные. В рассматриваемом примере это метод `view_model.add_button(name, path)`, где `name` — название кнопки, а `path` — путь к исполняемому файлу. Важно отметить, что View не выполняет никакой валидации или бизнес-логики — он лишь передает данные в ViewModel, следуя принципу разделения ответственности.

**3. ViewModel → Model (делегирование операции)**

ViewModel получает команду от View и делегирует выполнение операции модели данных. Внутри метода `add_button()` класса `ButtonViewModel` происходит вызов метода `self._model.add_button(name, path)`, где `self._model` является ссылкой на экземпляр `ButtonListModel`. ViewModel выступает в роли посредника между View и Model, обеспечивая слабую связанность компонентов.

**4. Model → выполнение бизнес-логики**

Model получает запрос от ViewModel и выполняет бизнес-логику операции. В методе `add_button()` класса `ButtonListModel` происходит:

- Проверка уникальности имени кнопки через метод `is_button_name_unique(name)`
- Создание нового объекта `ButtonModel` с указанными параметрами
- Добавление объекта в внутренний список `self._buttons`
- При необходимости — сохранение данных в JSON-файл через метод `save_buttons()`

Model не имеет информации о существовании View или ViewModel, что обеспечивает возможность его независимого тестирования и переиспользования.

**5. ViewModel → испускание сигнала**

После успешного выполнения операции в Model, ViewModel инициирует уведомление об изменении данных. В методе `add_button()` класса `ButtonViewModel` после вызова `self._model.add_button(name, path)` выполняется `self.buttonsChanged.emit()`, где `buttonsChanged` является сигналом Qt, определенным как `Signal()` в классе `ButtonViewModel`. Данный механизм обеспечивает одностороннюю связь от ViewModel к View без создания прямой зависимости.

**6. View → обновление интерфейса**

View получает сигнал `buttonsChanged` от ViewModel через механизм сигналов и слотов Qt. При инициализации `MainWindow` выполняется подключение сигнала к слоту: `self.view_model.buttonsChanged.connect(self.update_buttons)`. При получении сигнала вызывается метод `update_buttons()`, который:

- Очищает текущее отображение пользовательских кнопок, сохраняя служебные кнопки ("Добавить", "Удалить", "Закрыть")
- Получает актуальный список кнопок из ViewModel через метод `self.view_model.get_buttons()`
- Для каждой кнопки создает новый виджет `QPushButton` с соответствующими параметрами
- Динамически рассчитывает размеры кнопок на основе длины текста
- Добавляет кнопки в интерфейс в правильном порядке
- Подключает обработчики событий для запуска программ при нажатии на кнопки

**Особенности реализации:**

1. **Отсутствие прямой связи Model → ViewModel**: Model не уведомляет ViewModel напрямую об изменениях. ViewModel сам инициирует изменения через вызовы методов Model и самостоятельно испускает сигналы после выполнения операций. Такой подход упрощает архитектуру и делает поток данных более предсказуемым.

2. **Использование сигналов Qt**: Механизм сигналов и слотов Qt обеспечивает асинхронную коммуникацию между ViewModel и View, что предотвращает блокировку интерфейса и обеспечивает реактивность системы.

3. **Интерфейсы для слабой связанности**: View зависит от абстрактного интерфейса `IButtonViewModel`, а не от конкретной реализации, что позволяет легко заменять реализации и создавать mock-объекты для тестирования.

**Преимущества реализованного подхода:**

- **Тестируемость**: ViewModel и Model могут тестироваться независимо от View с использованием unit-тестов. ViewModel может тестироваться с mock-объектами Model, а Model — без наличия View или ViewModel.

- **Переиспользование**: Одна ViewModel может использоваться с различными представлениями (например, `MainWindow` и `DeleteButtonsDialog`), что обеспечивает гибкость архитектуры.

- **Разделение ответственности**: Каждый компонент имеет четко определенную роль: View отвечает только за отображение и обработку пользовательского ввода, ViewModel — за преобразование данных и управление состоянием представления, Model — за бизнес-логику и работу с данными.

- **Поддерживаемость**: Изменения в одном компоненте не требуют модификации других компонентов, что упрощает сопровождение и развитие системы.

- **Расширяемость**: Добавление новых функций (например, редактирование кнопок, сортировка) требует изменений только в соответствующих компонентах без влияния на остальную систему.

Таким образом, реализация паттерна MVVM в стартовой панели обеспечивает четкое разделение ответственности, высокую тестируемость и поддерживаемость кода, что соответствует принципам современной разработки программного обеспечения.

#### 2.2.4.5.6. Обработка ошибок и исключительных ситуаций

Механизм взаимодействия включает обработку ошибок на различных уровнях:

**1. Уровень операций с файлами**

- `FileOperations` обрабатывает ошибки доступа к файлам
- Ошибки логируются через `DialogManager`
- Пользователю отображается понятное сообщение об ошибке

**2. Уровень парсинга**

- `FileParserService` обрабатывает ошибки парсинга (некорректный формат, поврежденный файл)
- При ошибке парсинга файл отображается как plain text
- Ошибки не прерывают работу приложения

**3. Уровень кэширования**

- Ошибки доступа к кэшу обрабатываются gracefully
- При недоступности кэша выполняется прямой парсинг файла
- Используется механизм fallback для обеспечения работоспособности

#### 2.2.4.5.7. Производительность и оптимизация взаимодействия

Для обеспечения производительности применяются следующие механизмы:

**1. Дебаунсинг событий**

`FileWatcher` использует дебаунсинг для группировки быстрых последовательных изменений:

- Задержка 300 мс перед обработкой события
- Предотвращение избыточных обновлений при частых изменениях файла
- Использование `QTimer` с `setSingleShot(True)`

**2. Ленивая загрузка**

Редакторы создаются только при необходимости:

- Редактор создается при открытии файла, а не при инициализации приложения
- Данные загружаются из кэша при наличии, парсинг выполняется только при необходимости

**3. Фоновый парсинг**

Тяжелые операции парсинга выполняются асинхронно:

- `BackgroundParser` выполняет парсинг в отдельном потоке
- UI остается отзывчивым во время парсинга
- Приоритизация задач позволяет обрабатывать видимые файлы в первую очередь

**4. Кэширование результатов**

Двухуровневая система кэширования минимизирует повторные операции:

- `MetadataCache` обеспечивает быстрое отображение структуры
- `ContentCache` хранит полное содержимое для мгновенного доступа
- Инвалидация кэша происходит только при реальных изменениях файлов

Таким образом, механизм взаимодействия компонентов обеспечивает слабую связанность, высокую производительность и расширяемость системы, что соответствует принципам современной разработки программного обеспечения.

4. **Расширяемость**: Возможность создания собственных лексеров и стилей позволяет адаптировать подсветку под специфические требования проекта.

5. **Интеграция с Qt**: Результаты работы Pygments легко преобразуются в формат, совместимый с QTextCharFormat для применения в QTextEdit и других виджетах Qt.

**Использование в проекте**: Pygments применяется в модулях подсветки синтаксиса (`STHighlighter`, `MarkdownHighlighter`) для визуального выделения различных элементов кода (ключевые слова, строки, комментарии и т.д.) в редакторах файлов.

### 2.2.5.5. Система хранения данных

**JSON и файловая система**

В качестве системы хранения данных выбраны JSON-файлы и файловая система вместо реляционной базы данных по следующим причинам:

1. **Простота развертывания**: Отсутствие необходимости в установке и настройке СУБД упрощает развертывание приложения и снижает требования к системным ресурсам.

2. **Прямая доступность данных**: Файлы JSON и рабочие файлы пользователя доступны напрямую через файловую систему, что позволяет пользователю легко создавать резервные копии, переносить данные и редактировать конфигурацию вручную при необходимости.

3. **Читаемость и отладка**: Текстовый формат JSON легко читается и редактируется человеком, что упрощает отладку и поддержку приложения.

4. **Достаточность для задачи**: Для однопользовательского приложения с относительно небольшими объемами данных файловая система и JSON обеспечивают достаточную производительность без избыточной сложности СУБД.

5. **Встроенная поддержка в Python**: Стандартная библиотека Python предоставляет модуль `json` для работы с JSON, что исключает необходимость в дополнительных зависимостях.

**Использование в проекте**: 
- JSON-файлы применяются для хранения конфигурации (`buttons.json` — настройки кнопок стартовой панели, `saved_files.json` — реестр внешних файлов, `root_folder_path.json` — конфигурация корневой папки)
- Файловая система используется для хранения рабочих файлов пользователя (ST и Markdown файлы в папке `bookmarks/`)

**Использование в проекте**: Инструменты тестирования применяются для модульного тестирования (`tests/unit/`), интеграционного тестирования (`tests/integration/`) и тестирования менеджеров (`tests/managers/`).

## 2.2.6. Структура модулей приложения

### 2.2.6.1. Основные модули

**Модуль `src/ANTLR4/`**
- Назначение: грамматики ANTLR4 для парсинга различных языков программирования
- Подмодули:
  - `st_grammar/` — грамматика для Structured Text файлов
  - `one_c_grammar/` — грамматики для языка 1C (BSL, SDBL)
  - `py_grammar/` — грамматика для Python
  - `java_grammar/` — грамматика для Java
  - `ch_grammar/` — грамматика для C#
- Структура каждого подмодуля:
  - `.g4` файлы — определения грамматик
  - Сгенерированные файлы: `*Lexer.py`, `*Parser.py`, `*Listener.py`

**Модуль `src/parsers/`**
- Назначение: парсинг файлов и управление кэшированием
- Основные компоненты:
  - `file_parser_service.py` — сервис парсинга, координатор парсеров
  - `st_file_parser.py` — парсер ST-файлов
  - `md_file_parser.py` — парсер Markdown-файлов
  - `content_cache.py` — кэш полного содержимого (LRU)
  - `metadata_cache.py` — кэш метаданных (TTL)
  - `background_parser.py` — фоновый парсинг для оптимизации

**Модуль `src/editor/`**
- Назначение: система редакторов для различных типов файлов
- Основные компоненты:
  - `base_editor.py` — абстрактный базовый класс редактора
  - `st_editor.py` — редактор ST-файлов с иерархическим представлением
  - `markdown_editor.py` — редактор Markdown с предпросмотром
  - `plain_text_editor.py` — простой текстовый редактор
  - `editor_factory.py` — фабрика для создания редакторов
  - `editor_manager.py` — менеджер редакторов, координатор работы

**Модуль `src/managers/`**
- Назначение: менеджеры для координации работы различных подсистем
- Основные компоненты:
  - `tree_model_manager.py` — управление моделями дерева файлов
  - `file_manager.py` — управление файловыми операциями
  - `ui_manager.py` — координация пользовательского интерфейса
  - `toolbar_manager.py` — управление панелями инструментов
  - `dynamic_tabs.py` — управление динамическими вкладками

**Модуль `src/models/`**
- Назначение: модели данных для представления структуры приложения
- Основные компоненты:
  - `st_md_file_tree_model.py` — модель дерева файлов для Qt
  - `st_md_file_tree_item.py` — элемент дерева файлов

**Модуль `src/start_panel/`**
- Назначение: стартовая панель приложения (реализация MVVM)
- Структура:
  - `models/model.py` — модель данных кнопок
  - `view_models/` — ViewModel компоненты
  - `views/` — View компоненты (окна)

**Модуль `src/ui/`**
- Назначение: пользовательский интерфейс, созданный в Qt Designer
- Компоненты: UI-файлы и их Python-обертки

**Модуль `src/utils/`**
- Назначение: вспомогательные утилиты
- Компоненты:
  - `cache_manager.py` — управление кэшами
  - `clipboard_manager.py` — работа с буфером обмена
  - `delta_processor.py` — обработка изменений (delta operations)

**Модуль `src/observers/`**
- Назначение: система наблюдения за изменениями
- Компоненты:
  - `file_watcher.py` — отслеживание изменений файлов
  - `my_base_observer.py` — базовый класс наблюдателя

**Модуль `src/controllers/`**
- Назначение: контроллеры для обработки пользовательских действий
- Компоненты:
  - `selection_controller.py` — контроллер выделения в дереве файлов

**Модуль `src/operation/`**
- Назначение: операции с файлами и данными
- Компоненты:
  - `file_operations.py` — файловые операции
  - `delta_operations.py` — операции с изменениями (delta)

**Модуль `src/global_var/`**
- Назначение: глобальные переменные и конфигурация
- Компоненты:
  - `config.py` — управление конфигурацией приложения

### 2.2.6.2. Точка входа приложения

Файл `main.py` является точкой входа приложения и выполняет следующие функции:

1. Инициализация Qt-приложения (`QApplication`)
2. Загрузка конфигурации через `config.load_config()`
3. Создание модели данных (`ButtonListModel`)
4. Создание ViewModel (`ButtonViewModel`)
5. Создание главного окна (`MainWindow`)
6. Запуск главного цикла приложения (`app.exec()`)

## 2.2.7. Заключение по разделу

В данном разделе представлена архитектура и структура разработанного программного средства. Приложение построено на основе многослойной модульной архитектуры, что обеспечивает четкое разделение ответственности между компонентами и упрощает поддержку и развитие системы.

Ключевые особенности архитектуры:
- Использование паттернов проектирования (MVVM, Factory, Observer, Singleton, Strategy) для обеспечения гибкости и расширяемости

- Кроссплатформенность благодаря использованию Python и Qt6

Структура приложения организована в виде модулей с четко определенными обязанностями, что соответствует принципам SOLID и обеспечивает возможность независимого тестирования и развития отдельных компонентов системы.
